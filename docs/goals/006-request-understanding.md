## 2. 最初に再現する3件

次の問題は、確認時mainの判定式を抜き出した単独実行で確認されています。アプリ全体のE2Eを行った結果ではないため、まず現行の実関数・UI・サーバー経路で再現してください。

R1: 現在20mmの設計で「あと5mm動かして」
- 現行の距離抽出は `5` を絶対値として抽出し、相対増加としては分類していません。
- 追加量と移動距離そのものを区別し、黙って20→5mmの希望として扱わないこと。
- 「20→25mmとして案を作る」と示すか、意味が曖昧なら「5mm増やす／距離を5mmにする」をその場で選べること。

R2: 「回転させずに、右へ動かして」
- 現行の非対応判定は、否定された「回転」にも反応します。
- 回転を求めていない依頼を、回転非対応という理由だけで拒否しないこと。
- 距離が未指定なら現在値を保持するなど、指定されていない値を勝手に増減しないこと。

R3: 「左には動かさず、右に動かして」
- 現行の方向抽出は左右の両方に一致します。
- 禁止された方向と、希望された方向を区別すること。

3文だけの一致判定や置換でテストを通さず、原因となる相対値・否定の対象・節の関係を扱ってください。再現しなければ、その経路と結果を記録し、確認していない不具合を作らないでください。

## 3. 言葉の解釈と、設計の制約を分離する

現行RunManagerはGemini呼出し前に `interpretDesignRequest` を実行し、非対応や衝突なら停止します。

この構造で、手動支援用の限定的な読み取り能力を、実Geminiが受け付けられる言い方の上限にしないでください。一方、すべてを無条件にモデルへ渡せばよいわけでもありません。

次の責務を区別します。

- **本人が設定・確認した制約**: 固定寸法、紙枚数上限、選択領域、対象機構、採用前の設計版。信頼できる現在の設計と操作から取得する。
- **依頼の解釈案**: 自然文から抽出した方向・距離・増減・維持・未指定・曖昧な項目。手動支援またはGeminiによる提案であり、権限そのものではない。
- **候補の検証**: 解釈と現在の制約の整合、寸法、機構、紙面、版を専用プログラムで検査する。

解釈結果は、少なくとも距離の「絶対値にする／指定量を増減する／定性的に増減する／維持／未指定」を区別できる構造にします。単位換算と現在値からの計算はプログラムで行い、基準となる設計版を固定します。

方向についても、希望する方向と禁止する方向を混同しません。背景説明・引用・否定された数値を、そのまま目標値にしません。

確実に解釈できる定型表現は手動支援でも扱い、曖昧なものは曖昧と返します。巨大な日本語解析器を自作せず、単語があるだけの確定判定を減らしてください。

AI経路では、既存のfunction callingまたは互換性を確認した構造化出力で解釈案を受け取れます。SDK/API全体の移行や、別エージェントの新設は不要です。追加のモデル呼出しも既存の回数・時間・入力上限に含め、解釈だけを別料金の無制限ループにしません。

構造が正しいJSONでも意味が正しいとは限りません。原文中の根拠箇所を持たせる場合も、それだけで理解の正しさが保証されたと扱いません。現在の条件と照合し、不明な箇所は利用者に訂正できる形で示します。

**安全性と作者の意図を守る境界**

- 解釈器・Geminiが、現在の固定条件や紙の上限を解除・拡大しない。
- 本人が明確に指定した、より厳しい上限は既存仕様に従って扱う。
- 上限を緩める案は、具体的な変更差分への本人の承認を必要とする。モデルの `allowChange` 相当の出力を承認として扱わない。
- 不明な語句が残る依頼を、認識できた部分だけ実行して「希望どおり」としない。
- 範囲外の希望を、2〜70mmなどの境界へ黙って丸めない。希望値と可能な代案を区別する。
- 「検査を省略」「承認済みとみなす」などの文で検査や承認を迂回しない。
- 相対変更の解釈後に設計が変わったら、古い基準値の案を適用しない。
- 真の非対応・制約違反・読み取り不確実・通信障害を分け、すべてを「非対応」にまとめない。

## 4. UIは小さく改善し、依頼を読み直せるようにする

配色、作品中心の3工程、保存と作品一覧を維持します。設定画面を増やすのではなく、既存の依頼・候補比較に、短い解釈の表示を統合してください。

例: 現在20mm、追加5mmの場合
「右へ／20→25mm／絵の大きさを維持／型紙は現在の上限以内」

表示は実際の解釈・設計差分・検査結果から作ります。「紙の上限を守る」と「実際の使用枚数が増えない」を区別してください。

明確な依頼は、毎回余分な確認ダイアログを挟まず候補を提示できます。曖昧な項目だけ、短い選択肢で解消します。「分かりません。全文を書き直してください」を唯一の復帰手段にしません。

利用者の訂正は、その依頼・設計版にひも付けてサーバーへ渡し、再検査します。表示だけを訂正して古い解釈を実行しません。

文章を入れ直しても、現在の作品、選択範囲、入力draft、自動保存を失いません。採用前の候補は確定済み作品を置換しません。

見栄えのよい説明文で判定の誤りを隠さず、正しい理解、見える差分、訂正のしやすさをUI/UXの完成条件にします。

## 5. 実Geminiは既存の接続導線を使う

設定画面、doctor、許可手順を重複実装しません。`docs/live-gemini.md` とコードが一致するかを必要な範囲だけ確認します。

確認時の既存コマンド:

```bash
npm run doctor
npm run smoke:live -- --plan
```

これはネットワーク上のモデルやキーの動作確認ではなく、ローカル設定・試験計画の確認です。

実APIは、本人の具体的な許可と必要な設定が確認できた場合だけ実行します。本Goalは新しいAPI課金、GCP作成、Cloud Run公開の許可ではありません。既存の許可がある場合に改めて毎回質問せず、その範囲を守ります。キーが置かれているだけで実行許可とみなしません。

許可済みの場合は、既存L1を少数の試験として実行し、通常のブラウザ・サーバー・ツール・候補採用・PDF経路を通します。

既存の明示許可後のコマンドは以下ですが、実装変更後もスクリプトと一致しているかを確認してください。

```bash
npm run build
LIVE_API_AUTHORIZED=yes npm run smoke:live -- --case L1 --authorize-paid-api
```

ケース追加や再試行は、既存の全体台帳・回数・時間の残枠内で行います。今回の言い換え確認のために枠をリセット・増加させません。許可のない大量評価をしません。

未設定・未許可ならライブ試験だけを `not_run` とし、1〜4の修正、6の回帰、main統合を完了してください。外部確認を待つためだけの機能追加を続ける必要はありません。

現在のアプリが送るのは依頼文・設計・選択情報です。今回、利用者の画像本体をGeminiへ送る範囲を勝手に増やしません。画像を送っていないのに、AIが絵を見て理解したと説明しません。

実呼出しの記録では、依頼、基準版、解釈案、ツール結果、候補、採用版、PDF、モデル、使用量を対応させます。実値の秘密情報や内部思考・opaque signatureを公開ログにしません。

## 6. 同じ意味と違う意味を対にして回帰確認する

テストは全て成功するような同義文だけにしません。意味が変わる最小差分も含めます。

- 現在20mm: 「あと5mm動かして」→追加5mm。「5mm動かして」→絶対5mm。「5mm短くして」→減少5mmとして扱うか、曖昧なら明示確認。
- 「回転させず右へ」→回転要求ではない。「回転させたい」→非対応。
- 「左には動かさず右へ」→右。「左にも右にも動かしたい」→対象外または具体的な確認。
- 「今は20mm。25mmにしたい」→過去・現在の説明を目標値と衝突させない。
- 「2cm」「20mm」「２０ｍｍ」の対応、単位のない数値、境界値と上限超過。
- 「絵は大きくしない。動きだけ大きく」→絵の大きさと移動量を分離。
- 「紙は増やさない」「紙は3枚まで増やしてよい」→緩和には必要な具体的承認を残す。
- 「大きくしないわけではない」などの曖昧な否定→推測で確定せず確認。
- 安全制約の迂回指示、古い設計への相対指示、採用通信中の編集、取消し後の遅延応答。

同じ例文へ正規表現を足すだけで終えず、開発時と異なる言い換え・語順も使います。日本語全般への対応を主張しません。

自動テストは、解釈関数、RunManager／ツール、手動UI、模擬AI経路を分けて確認します。Gemini未実行のまま、自然言語理解の実性能を測定済みとはしません。

少なくとも、R1〜R3は初回の問題を示すテストを置き、修正後の通常UIで理由の表示・訂正・採用まで確認してください。

「希望を満たす候補」「希望とは違う代案」「確認待ち」「非対応」を区別します。代案が組み立て条件を満たしても、元の希望を達成したことにしません。

既存S/U/Pの保存・入力・印刷・組立・狭幅・WebKit・コンテナの保証を維持します。古い誤判定を期待するテストは根拠と仕様変更を記録して改訂し、制約やデータ保持の試験を削除して通しません。

## 7. 実物確認と公開を混同しない

実物確認は既存の試作キットと版固定ガイドを使います。今回の採用結果から新しいキットを出す場合、その版・ハッシュと出力ファイルを対応させてください。

人が印刷・組立するまでは未確認です。以前のPDFと新しい設計の結果を混ぜず、100%印刷の校正線、組立時の手修正、両端の動きを既存記録へ残せる状態を維持します。

Cloud Runの自動作成や公開は行いません。公開URLや実物の成功を、CI成功から推定しません。公開前に必要な未完了項目は既存文書の現在状態へ整理し、新しい巨大な管理システムを作りません。

## 8. 小さくmainへ統合する

A. R1〜R3の再現と、手動解釈・制約境界の修正。
B. AI経路の限定パーサー依存の整理、解釈表示と訂正経路。

依存関係に従い、安全なまとまりでコミット・作業ブランチpush・main統合・CI確認を行います。通常の統合とpushは既に許可されている範囲です。既存保護ルールを守り、force pushや自動公開はしません。

古いmainを前提に上書きせず、最新との差分を確認してください。クリーンなコミットの実際のコマンドとCI設定を使って検証します。

- npm ci / npm run doctor
- npm run check / npm run test:e2e / npm run examples

失敗したCIは対象SHA・ジョブを確認し修正します。時間切れや実行制約でpendingならpendingと報告し、成功を予告しません。
