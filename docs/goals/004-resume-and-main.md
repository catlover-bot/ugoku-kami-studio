# Goal 004-R — 外部確認待ちを分離し、mainへ統合しながら開発を継続する

うごく紙工房の開発を、現在のWSLの作業状態から再開してください。

今回の最優先は、
「既存成果の確認 → コミット → main統合・push → CI確認」
です。

その後、実行可能な実装・使用感の改善を進め、
検証した変更を小さな単位でmainへ統合してください。

計画書だけで終了せず、実際の変更・Git操作・検証を行ってください。

## 1. 今回の許可と、以前の指示の更新

対象リポジトリに限り、利用者は今回、次を実行対象として指定します。

- 確認済み変更のローカルコミット。
- 作業ブランチのpush。
- 検証済み変更のmainへの通常統合とpush。
- 必要なPRの作成と、既存要件を満たした後の通常マージ。
- 通常のGitHub Actions CIの実行・確認・不具合修正。

以前のGoalの「push・PRは別途許可待ち」は、
この範囲では今回の指示で更新します。
mainへの反映を繰り返し確認しないでください。

「古いindexを保持し続ける」ことは目的ではありません。
既存成果を失わず、検証した最新版をコミットしてください。

以下は許可に含めません。

- force push、履歴破壊、ブランチ保護・必須レビューの解除。
- 秘密情報、個人画像、未確認の第三者素材の公開。
- 新しいAPI課金、GCPリソース作成、IAM変更、Cloud Run公開。
- 有料の追加ランナー購入や、無断のOS全体の変更。

mainへのpushでデプロイや実API試験が起動しないか、
workflowと関連スクリプトを先に確認してください。
通常CIと、課金・公開の操作は分離します。

## 2. Goal全体を外部確認待ちにしない

次を別々の状態として管理してください。

A. ローカル実装・自動検証
B. コミット・main統合・push
C. GitHub CI・コンテナ検証
D. 実Gemini
E. 印刷・組立・実物
F. 初見の人・実スマートフォン
G. Cloud Run公開

D〜Gに不足があっても、独立して進められるA〜Cを止めません。
実物結果は、main統合やCIの前提ではありません。

ただし、実Gemini未実行や実物未確認は、そのまま記録します。
手動モードのソフトウェア統合と、
製品の実物検証完了を混同しません。

できる作業が本当に完了した場合は、
「ソフトウェア統合済み／外部検証は未完了」と報告します。
中断を避けるためだけに、不要な機能・文書・模擬テストを増やしません。

## 3. 現在の作業状態を読み、成果を保護する

作業場所:
~/workspace/ugoku-kami-studio

origin:
catlover-bot/ugoku-kami-studio

直近の報告:
check 97件、E2E 92件、examples 4例が成功。
実Gemini・実物は未確認。

これは引継情報です。今回の実行結果と区別してください。

最初に以下を確認します。

- pwd、origin、HEAD、ブランチ、git status。
- ステージ済み・未ステージ・未追跡の変更。
- git worktree list。
- Git作成者設定、既存のpush認証。
- README、AGENTS.md、Goal 001〜004。
- package.json、lockfile、既存CI、Dockerfile。
- docs/verification.md、docs/live-gemini.md、
  試作PDFと対応する設計データ。

最新実装はこの作業ツリーにあります。
GitHubのREADMEだけのmainで上書きしません。

Goal別のブランチ名があっても、
そのブランチに実装がコミット済みとは限りません。
空の旧ブランチを順番にマージして完了とせず、
現在の最新版を取り込んでください。

reset --hard、git clean、無断のstash、
再クローンによる置換、無関係な差分の削除はしません。

## 4. 作成者設定・認証を確認する

有効な本人のGit設定があれば尊重し、上書きしません。

未設定の場合は、実行環境の認証と本人情報を確認し、
このリポジトリだけに設定して構いません。

確認対象の本人情報:
- GitHub login: catlover-bot
- GitHub user ID: 203637895
- 表示名: m.hirotaka

同じ本人と確認でき、設定がない場合は、
確認済み表示名と、GitHub公式のID付きnoreply形式
203637895+catlover-bot@users.noreply.github.com
を利用できます。

git config --localに限定し、globalは変更しません。
個人メールを推測・転載せず、web-flowや別人を作成者にしません。

Gitの作成者設定とpush認証は別々に確認します。
既存のGit/gh/SSH認証を利用し、トークンをログへ出しません。

本当に本人情報や認証が不足する場合だけ、
その操作を保留にし、必要な設定を一度具体的に示します。
ログイン待ちで独立した開発まで停止しません。

## 5. 最新版を検証可能なコミットにする

既存indexも含め、変更内容と公開してよい対象を確認します。

.env、APIキー、認証JSON、ユーザー画像、
秘密を含むログ、node_modules、不要な巨大成果物を混ぜません。
秘密らしい値を見つけても実値を出力しません。

git add .やgit add -Aで一括追加せず、
確認したパスを指定します。

古いステージ内容のままコミットせず、
テストした最新版とコミット内容を一致させます。

既に未pushのコミットがある場合は、
これから公開される履歴も確認してください。
最終版から秘密を消しただけで、
秘密のある過去コミットをpushしてはいけません。

最初の統合が大きなまとまりでも、
過去のGoalごとの履歴を人工的に作る必要はありません。
内容を明示したコミットへ記録し、その後は小さな変更に分けます。

実際のpackage.jsonを確認し、
npm ci
npm run check
npm run test:e2e
npm run examples
を実行します。

コミットされた状態をクリーンな別worktree等でも確認します。
元の未追跡ファイルや残存buildに依存した成功を見逃しません。
既存の作業ツリーとサーバーは保護します。

修正が必要なら追加コミットし、
最終的に検証した状態を統合対象にしてください。

## 6. mainへ統合してpushする

基本の流れ:

確認済みコミット
→ git fetch originと履歴確認
→ 作業ブランチpush・統合前CI
→ mainへの通常統合
→ mainのpush
→ 対象SHAのCI確認

未コミット変更を抱えたまま、
mainへのswitch/pull/mergeを行いません。

無関係な差分を元ツリーに残す必要がある場合は、
クリーンな別worktree等で統合作業を行います。

mainからfast-forwardできるなら、その方法で構いません。
mainが進んでいれば差分を取り込み、
競合を内容で解決して再検証します。

非fast-forwardの拒否をforce pushで突破しません。
ours/theirsの一括適用で片側の成果を捨てません。

mainに保護ルールがあれば、PRと既存の必須要件を使います。
保護解除や管理者バイパスは行いません。
必須の人間レビューがあれば、そのレビューだけを保留にします。

通常の直接pushが可能なら、
検証済みの統合をmainへpushして構いません。
形式だけのPR待ちを新しい停止理由にしません。

古い開発ブランチは無断削除しません。

push後はリモートmainのSHAとtreeを実際に確認します。
他の更新がなければローカルmainとorigin/mainの一致、
他の更新があれば自分の統合が含まれることを確認します。

pushコマンドを実行しただけで、
main反映済みと報告しないでください。

## 7. CIを動かし、失敗した場合は原因を直す

既存CIを利用し、
作業ブランチpushまたはmain宛てPRで統合前に、
mainへのpushで統合後に検証できるようにします。

通常CIはGeminiキー・GCP認証・課金APIなしで動くこと。
lockfileからの導入、check、E2E、examplesを確認します。

Playwrightやフォントなど、
必要なテスト環境を明示して再現可能にします。
通常検証の権限はcontents: readを基本にします。

CIが失敗した場合は、対象SHA・ジョブ・ステップを読み、
原因を修正して再実行します。

テスト削除、continue-on-error、
根拠のない期待値変更で成功扱いにしません。
成功・失敗・未起動・pending・skipを区別します。

WSLにDockerがなくても、
利用可能な標準GitHubホストのLinuxランナーで
既存Dockerfileのbuild・起動・health・手動画面を確認してください。

レジストリへのpushやCloud Runデプロイは不要です。
GitHub側でも実行不可なら、その制約を記録します。
設定しただけでコンテナ検証成功とは書きません。

## 8. 統合後も、価値に直結する改善を進める

初回のmain反映を後回しにして、
さらに大きな新機能へ着手しないでください。

統合後、実コードと画面で残課題を確認し、
未実装・不具合があれば次を優先します。

- 自分の画像→選択→条件指定→候補比較→採用→キット取得が、
  PCと狭い画面でつながる。
- AI未接続・失敗・中断でも、手動編集と保存を続けられる。
- プレビュー、型紙、部品、組み立て手順が同じ設計版に対応する。
- 印刷対象と実物記録が、その後の編集で別版へ付け替わらない。
- 保存・復帰・却下・Undoで作品を失わない。
- docs/live-gemini.mdと実コードの設定名・起動手順が一致し、
  設定後は既存のL1試験へ進める。

すでに成立しているものは二重実装せず、回帰確認だけにします。

直線運動1機構とGoal 003のデザインを維持します。
新機構、画像生成、SNS、会員登録、
全面的なUI刷新は追加しません。

実物の摩擦や耐久性を机上テストで検証済みにせず、
模様ずれなど残る制約も隠しません。

各改善は最新mainを基点にした短い作業ブランチで進め、
検証後にmainへ統合します。

## 9. 最終報告

本指示をdocs/goals/004-resume-and-main.mdに記録し、
古いpush禁止やGoal全体blockedの記述が
今後の誤停止を招かないよう、現在の方針を追記します。
過去の検証結果は改ざんしません。

最終報告には次を含めてください。

1. mainに統合した内容、GitHub上のmain SHA、コミットURL。
2. 統合方法、push結果、PRを使った場合はその状態。
3. CIの対象SHA、実際のrun URL、結果。
4. 今回修正した利用者価値と、確認した操作。
5. クリーン環境での実行コマンドと結果。
6. 未コミット・未追跡・除外したファイルの範囲。
7. 実Gemini・実物・初見の人・実機・公開の個別状態。
8. 本人にしかできない残作業と、正確な設定・印刷対象。

実行できない操作や未確定のCIは正直に記録します。
必要なファイルを削除してcleanにしたり、
将来の成功を約束したりしません。

単に「外部確認待ちなのでGoal全体blocked」で終了せず、
この実行で進められる統合・修正・検証を実施してください。
