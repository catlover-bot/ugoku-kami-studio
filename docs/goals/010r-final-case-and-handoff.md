## 2. Cを始める前のローカル確認

Cだけを選択実行できるよう、既存driverを小さく調整します。A/Bを自動再実行するall-only構成にしません。接続確認のための「こんにちは」やデモ撮影用の別生成も不要です。

1. 前回Cの試験入力・採用前の設計・保護条件を既存のJSONから取得する。コアで実際に不成立であることを先に確認する。70mmだから常に不成立と決めつけず、その入力に対する根拠を残す。
2. 認証・健康確認・静的な画面検証と、モデルを起動する操作を分ける。単なる接続確認でAI開始枠を消費しない。
3. 毎分の窓は、完了時刻ではなく受理された開始を基準にする。中断も開始枠を消費する既存仕様を維持する。
4. scripts/trial-request-window.tsの60秒＋余裕1秒を利用し、古い手順に未反映ならdriverへ接続する。全ケース固定sleepの追加や制限値の緩和で回避しない。
5. モデル開始前の429、Vertex側429、既に送信した後の失敗を区別する。記録が足りなければ送信0と断定しない。
6. retryAfterの情報を返す実装があるなら尊重する。現在はない場合に追加するなら、実際のサーバー制限窓から算出し、根拠のない残秒数を表示しない。

既存の待機計算・台帳を二重実装しません。時計・開始窓・予約の検証は課金なしで先に行い、実環境の枠を手順のデバッグに使わないでください。

## 3. Cの受入条件

通常UI→実サーバー→実Vertex→既存コアという同じ経路を使います。応答の差し替え、サンプルだけの固定回答、検証器を迂回した候補は使いません。

- 正しい対象の実モデルへ要求が到達した証拠がある。
- 元の要求値・固定条件・紙上限・設計版を維持し、違反する案を採用可能にしない。
- 要求した動きがその条件で成立しないこと、または確認・条件変更が必要なことを、利用者が区別できる。
- 代案を出す場合は既存コアで検査し、要求値との差と条件変更の有無を示す。自由文の数字を検査済み候補にしない。
- 成立する代案が見つからない場合でも、適切な理由と次の操作を示し、原本を保持できれば、不成立を安全に扱えた結果として記録する。特定の42mm案を出すことは合格条件ではない。
- 「AI処理が終わった」「不成立を適切に扱えた」「要求どおりの工作案が成立した」は別の判定にする。
- 生成中・拒否・未採用の状態で画像・選択・確定版・保存データを変更しない。条件を変えるかは本人が決める。
- 権限や幾何検査の失敗を、無条件な「すべての配置で不可能」という断定へ変えない。

429のままなら実モデルCは未検証です。コアが拒否できたことと、モデルが適切に説明・再提案できたことを別々に記録してください。モデルが誤った回答を出しても、安全な原本保持と回答品質を分けて報告し、無制限の再試行で成功例を作りません。

Cが一度確認できたら、成功率を増やす追加生成やA/B再試験をしません。片付けと素材更新へ進みます。
