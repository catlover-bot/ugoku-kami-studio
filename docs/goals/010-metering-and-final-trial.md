このプロンプトを利用者が実装エージェントへ送った場合、以下の範囲で非公開試験の継続を承認します。

- 前回のVertex限定試験分を含め、クレジット控除前の合計5米ドルを管理目安とする。追加で5米ドルを付与する意味ではない。
- 前回分の費用推計・予備・送信済み不明額を引き継ぐ。台帳をリセットしない。
- 実AI依頼は残り最大3件。診断用の生成、失敗、再試行も数える。前回1件と合わせて最大4件。
- モデル呼出しは1依頼最大6回。前回2回を含め全体24回以内。この条件では新規3依頼の最大18回を超えない。
- 前回分を含むCloud Run稼働は累計最大2時間、Cloud Buildは累計最大60分。
- Cloud Runは前回と同じ東京・app 1 vCPU / 1 GiB、min0/max1、AI同時1、IAM認証付き。既存の非同期処理が継続するCPU割当を維持する。
- Vertexは既存のgemini-3.8-flash / global / LOWを維持。プロジェクトと請求先は既に確定した対象を使う。
- 試験に必要な専用リソースの再作成、最小限IAM、ビルド、限定デプロイ、本人認証での操作、結果保全、試験後の削除をこの範囲に含める。
- 5米ドルは厳密な請求遮断額ではない。開始前・各モデル送信前に費用見込みと残り枠を照合し、次の処理が入らない場合は送信しない。
- 現在の上限のまま3件を完了できるとは仮定しない。入らない場合は、枠不足の具体的な数値だけをまとめて報告する。

一般公開、長期運用、予算追加、モデル変更、GPU、Developer APIへの切替、新しい有料基盤、請求先変更、YouTube公開、Zenn最終提出は対象外です。確認済みのログイン・プロジェクト用途・残高を再質問しません。クーポンの終了日・適用範囲は未確認のまま控除0とし、今回の試験の停止理由に戻しません。

## 2. 使用量が「ない」のか、判定が厳しすぎるのかを分ける

現行vertexUsageCostUsdはpromptTokenCount、candidatesTokenCount、thoughtsTokenCount、totalTokenCountのすべてを要求します。thoughtsTokenCountが無いだけでもnullになります。一方、公式SDKでは使用量の各フィールドはoptionalです。ただしoptionalであることだけを根拠に、無い値を0にしてよいとは判断しません。

以下をSDKの受信直後から順に追跡してください。

1. HTTP応答とSDKのusageMetadataに何があるか。
2. providerの正規化で何が残るか。
3. runsの完全性判定と表示用集計が何を欠測にするか。
4. 永続台帳がどの記録を費用確定の根拠にするか。

既存の原記録で原因が分かれば、追加通信なしで再現します。生の使用量が保存されていなければ、過去の欠測理由は特定不能と明記し、再現用の合成fixtureを実応答と呼びません。新しい実応答の採取は、残り3件の通常試験に組み込みます。「こんにちは」のためだけに試験枠を消費しません。

記録はresponseId、試行ID、call番号、SDK版、モデル、finishReason、usageMetadataの許可した数値と各フィールドの存在・欠落・不正の区分に限定します。認証情報、画像、本文、内部思考、署名を診断ログへ追加しません。欠落・null・0・不正を区別します。後続の応答変換が失敗した場合や中断応答でも、観測できた使用量の記録を失わせません。

## 3. 費用の算定可能性を、全内訳の取得と混同しない

以下を区別します。

- usage-estimate：必要な内訳から計算できる使用量ベースの見積もり。請求明細ではない。
- aggregate-upper-estimate：総トークン数等に基づく保守的な見積もり。内訳を観測済みにしない。
- sent-unknown：送信済みで費用を十分に評価できない。保守的予約を維持する。
- reserved-not-sent：まだ送信していない処理の枠。
- billing-actual：本当に取得した請求明細。上記と分ける。

対象APIの公式仕様・SDK版を確認し、totalTokenCountの意味と、tool/thinking/cacheの包含関係を固定します。同じ課金対象を重複加算せず、値が矛盾するときは精算を保留します。

例えば、当該応答の信頼できるtotalTokenCountが全対象トークンを包含し、対象が今回のテキスト＋ツール呼出しのみで、単価表の最高単価も確認できる場合は、総量を最高単価で評価する保守的見積もりを検討できます。これでthoughtsTokenCountを0に埋めたり、正確な内訳を得たことにはしません。

同じ呼出しのpromptとtotalの意味・整合が確認できるなら、入力を入力単価、残りを高い出力単価で評価する方式も検討できます。根拠がない場合は使いません。時間窓のMonitoring集計を、そのまま個別応答のtotalTokenCountに代入しません。

単価はVertexの対象モデル・global・Standard・時点を確認し、Developer API料金や還元を混ぜません。公式単価が今回取得できなければ、既存の保守的単価を「従来の計画単価」と表示し、現在の単価として再確認済みにしません。

## 4. 未送信枠まで保持し続ける予算計算を直す

現行の予約にはTHINKING_RESERVE=65,536があり、前回は入力上限32,768bytes、出力設定2,048tokens、最大6callで3.336192米ドルを予約しています。

これは計画上の仮定であり、思考を65,536tokens使った観測ではありません。bytesを正確なトークン数とみなさず、maxOutputTokensやLOWがどこまで上限を保証するかも、公式仕様なしに決めません。

次を実装してください。

- 既存のローカル永続台帳を拡張し、依頼全体の予約と、モデルへの送信試行を対応付ける。
- 送信前の永続化、callの一意ID、再試行、重複実行、中断、クラッシュを扱う。
- 終了を確認した依頼で、未送信が証拠で確定した枠だけを解放する。送信したが応答不明の枠は維持する。
- 二層の予約は同じ支出の資金枠として照合し、外側の依頼予約と内側のcall予約を二重に費用として足さない。
- 残りのモデル送信について、その都度費用枠を確認する方式、または実際に許可するcall数だけを予約する方式へ改善する。クラッシュ・再起動で枠が復活しないこと。
- 単なるメモリ内カウンターを全体予算として扱わない。大規模な課金サービスや新しいクラウドDBの導入へ拡張しない。

前回2callだけが実際に送信されたことを、記録・SDK再試行設定・終了した処理と突合できれば、残り4call枠を保持する必要性を再評価できます。従来の同じ仮定では、2call分1.112064米ドルと、未送信4call分2.224128米ドルに分かれます。これらは予約計算で、実費ではありません。

過去台帳は原本を保全し、算定方式の版・根拠・前後差を追記します。応答が2個あることだけで、隠れた再試行がなかったと断定しません。欠測額を0にしたり、不明額を消して予算枠を作ったりしません。

必要なテスト：全フィールド、思考のみ欠落、totalのみ有効、metadata全欠落、値不整合、明示0、送信前停止、送信後中断、成功後の記録失敗、6枠中2送信で終了、全6送信、SDK再試行、二重精算、クラッシュ・再起動。前回の停止条件をfixtureで再現し、改善が何を変えたか示します。

## 5. 再試験前に、一度で枠を確認する

ローカルの修正と回帰を先に完了してください。新しいデプロイを始めてから、次の予約が全く入らないことを発見する進め方は避けます。

既存費用・不明分・予備、追加インフラ費用、3件の送信上限を同じ台帳で確認します。安全に評価できないときはクラウドを作りません。不足時は必要な追加額・何を確認すれば減るかだけをまとめ、クーポン画面や本人情報の再確認へ戻しません。

保守的見積もりで予算管理が成立するなら、正確な請求明細の到着そのものを実装と試験の前提にしません。別途明細を入手した際に照合します。新しいBigQuery課金exportは今回の必須条件にしません。

## 6. 残り3件は、次の順でまとめて実行する

すでに成功した初回20→25mmを、成功件数を増やすために繰り返しません。

1. **中断**：通常UIから実Vertex要求が始まったことを確認して中断。HTTP受理、サーバー状態、Abort、後続ツール・採用の禁止、原本と保存の保持を確認。先に正常完了した場合は中断成功と呼ばず、その試行として記録する。都合よく繰り返さない。
2. **中断後の別依頼**：同じブラウザから異なる成立する依頼を出す。実行枠の復帰、候補生成・検査・採用・同版PDF・ガイド・保存再読込を確認。これを「別依頼」と「中断後復帰」の両方の証拠にする。
3. **不成立条件**：本当にコア検査で成立しない希望を使う。未検査の助言を採用させず、保護条件を勝手に緩めない。希望との差や条件変更案を示し、原本と手動操作を維持する。

3件内に診断用metadata採取を組み込みます。実APIの中断はクライアントで採用を止めた事実と、提供者側の計算・請求が止まるかを分けます。外部側の停止を観測できない場合は保証しません。

プログラムで失敗を注入した試験、模擬AI、ローカルGemma、実Vertexを区別します。全試験を同じ未変更の配信SHAで行うのを基本にし、修正が必要なら対象SHAを分けます。

試験終了後はローカルに証拠を保存し、試験サービス・イメージ・secret・今回のSA/権限など、今回の専用資源だけを片付けます。原則終了時、遅くとも初回作成から24時間以内の既存方針を維持します。既存API・共有履歴・別用途の資源を消しません。削除保管の残存と費用も記録します。
