# Goal 004 — 実Geminiの設計を、印刷して動かせる作品につなぐ

うごく紙工房の実装を継続してください。
Goal 001〜003を作り直さず、現在の実装を使って、
「実Geminiによる設計変更 → 同じ設計版の型紙 → 実物確認」
をつなげることに集中してください。

詳細版のGoal 004が添付されていれば、その受入条件も読んでください。
文書や模擬テストだけを増やして終了しないでください。

## 1. 現状確認と成果の保全

対象は \~/workspace/ugoku-kami-studio、
originは catlover-bot/ugoku-kami-studio です。

直近の報告:

- ブランチ: feat/003-design-and-usability
- check 84件、E2E 76件、examples 4例が成功
- 実Gemini、初見の成人、実スマートフォン、実物、公開、
  Docker実起動は未確認
- 既存62ファイルのindexと、その後の未ステージ・未追跡変更がある

まず実際の状態と差分を確認し、既存成果を保護してください。
破壊的なreset、clean、無断のstash、再クローンはしません。

Gitの作成者情報が設定済みなら、内容・秘密情報・対象範囲を
確認した変更をローカルコミットして構いません。

以前の「indexを保持」は成果を消さないための指示です。
古いindexを保持し続け、最新実装を記録しないことを目的にしません。

既存indexも含めて内容を確認し、
確認したパスだけをステージしてください。
git add . や git add -A で無関係な変更を一括追加しません。

コミット対象とテストした実装の状態を一致させてください。
名前・メールを推測で設定しません。
push・PR・公開は別途明示的な許可がある場合だけ行います。

## 2. 実Geminiを使うための設定導線を完成させる

既存のSDK、設定読込、AI実行処理、smoke:liveを調べ、
別の実装や重複する設定系を新設しないでください。

実装に合う接続方式、認証方法、モデル、環境変数を確定し、
公式資料で互換性を確認してください。
推測のモデルIDや環境変数名を案内しません。

必要なのは、利用者が次の操作へ進める状態です。

- 必要な設定項目と、設定する場所が分かる。
- 秘密を表示せず、課金なしで設定確認できる。
- モデル、送信データ、実行上限、費用見積もりの根拠が分かる。
- 本人が実行を許可した後、確認済みのコマンドで試せる。

「APIキーと許可待ち」の一文だけで終わらず、
必要な設定と、その後に実行する正確なコマンドを残してください。

APIキーをチャット、Git、ブラウザ配信コードへ入れません。
実行許可前にエージェントが確認入力へ勝手にyesを返しません。

このGoalだけを、有料API実行・課金有効化・IAM変更・
クラウド作成の許可とは扱いません。

既存の具体的な許可がある場合は、その範囲内で実行します。
ない場合も、実装と設定導線の検証は完成させてください。

通常のcheck・E2E・CIで実APIを呼ばないようにします。

## 3. 実APIで確認するケースは、まず少数に絞る

L1: 成立する調整
「もう少し大きく動かしたい。絵の大きさは変えず、
紙も増やさない」

成立する余地がある設計で、実際のツール呼び出し、
検査、候補提示、採用、PDF更新まで確認します。
20→25mmなどの固定回答を返して成功させません。

L2: 両立しない条件
現在の設計に対して、本当に制約違反となる依頼を使います。
保護条件を黙って変えず、代案や条件変更の提案へ進むことを確認します。
検査の失敗や再試行を、見せ場のために作りません。

L3: 非対応の依頼
「回転させたい」などの依頼に対して、
直線運動へ黙って置換せず、元の作品を維持します。

最初はL1を1件実行し、必要な確認へ進みます。
既存の呼び出し・時間・入力上限を守り、
全ケースの合計上限も決めて、無制限に再試行しません。

「こんにちは」への返答は設計機能の合格条件ではありません。
少なくともL1は可能なら実ブラウザから操作し、
通常のアプリと同じサーバー・採用処理・出力経路を使います。

実行ID、モデル、ツール、検査結果、変更差分、使用量、
設計版とPDFの対応を、秘密を除いて記録します。

模擬応答、手動支援、実Geminiを混同しません。
ライブ未実行を成功件数に数えません。

## 4. 印刷して試す1作品を固定する

最初は白または透明背景の、対応範囲内の作品を選んでください。
模様背景のずれや枠をまたぐ輪郭は、別の未解決条件として残します。

同じ設計版から、以下をそろえてください。

- 原寸型紙
- 実際に必要な材料
- 部品に対応した組み立て手順
- 設計データと検査結果
- 始点・終点の画像
- 既存の実物確認フォーム

実Geminiの採用結果が得られたら、その版を試作します。
未接続なら手動設計の版で機構試作を先に進めてよいですが、
後から実Geminiの成果だったことにしません。

利用者へ渡す確認手順:

1. 100%で印刷し、50mm校正線の実測値を記録する。
2. 手順どおりに組めるか、工程外の修正が必要かを記録する。
3. 始点から終点まで動かし、引っかかりとガイドの保持を確認する。
4. 10往復程度の初期チェックを行う。耐久性保証とは呼ばない。
5. 正面・裏面・始点・終点を記録する。

人が行う印刷・組み立て・撮影を、実施済みにしないでください。
出力を手で直した場合も、元の型紙と変更内容を残してください。

実物で問題が出た場合は、部品・寸法・接着位置・工程を修正します。
画面だけのマスクや色で、実物の不成立を隠しません。

## 5. デザインは維持し、実際の迷いを直す

Goal 003の作品中心の画面とデザイントークンを維持してください。
配色やレイアウトの全面刷新はしません。

画像の選び直し、候補待ち、失敗、非対応、
印刷直前の操作が分かるかを確認します。

狭い画面は開始画面だけでなく、
画像選択・候補比較・印刷まで確認してください。

初見の成人が参加できれば、
「自分の画像 → 部分選択 → 条件指定 → 候補採用 → キット取得」
を説明なしで試してもらい、助言した箇所と完了可否を記録します。

参加者がいない場合は未実施です。
開発者自身やPlaywrightを、初見の人の確認として数えません。

新機構、画像生成、SNS、会員登録は追加しません。

## 6. 検証と最終報告

既存のcheck・E2E・examplesを実行し、回帰を修正してください。
過去の件数と追加試験を重複加算しません。

Dockerが利用可能なら既存コンテナを確認します。
未導入なら未実施とし、これを理由に実APIや試作準備を止めません。
無断のOS変更・クラウド公開へ作業を広げません。

成果物はartifacts/goal004/へ整理し、
設計版、PDF、実行モード、実物記録を対応させてください。
秘密情報や個人画像を公開成果物へ含めません。

最終報告:

1. 実Geminiで何が設計変更され、何が守られたか。
   未実行なら最初にそう書く。
2. L1〜L3の実行区分と結果。
3. 今すぐ印刷する1件のPDF、材料、手順、設計版の実際の保存先。
4. 実物、初見の人、実スマートフォンの確認状況。
5. 修正した不具合と残る制限。
6. 実行コマンド、回帰結果、使用量。
7. コミット、未コミット差分、push、公開の状況。
8. 利用者が次に行う正確な設定・コマンド・印刷対象。

実Geminiと実物が未確認なら、製品完成とは総括しません。
ただし外部確認待ちを理由に、設定導線や試作準備まで止めないでください。
