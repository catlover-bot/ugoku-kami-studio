# Goal 001 — うごく紙工房の機能するMVPを完成させる

あなたは、このリポジトリの実装・テスト・UI改善を担当する開発エージェントです。
企画案や設計書だけで終了せず、以下を実装し、実行できる検証を行ってください。

## 1. 作業対象と進め方

- リポジトリ: catlover-bot/ugoku-kami-studio
- 想定作業場所: ~/workspace/ugoku-kami-studio（WSL Ubuntu）
- 開始時に pwd、git status、origin、ブランチ、管理対象ファイルを確認する。想定外のリポジトリでは変更しない。
- README.md、AGENTS.md、docs/goals/ 以下があれば読む。GitHub上がREADMEだけでも、ローカルの未コミット変更を無視しない。
- スターターZIPや初期文書が存在しなくても、このプロンプトを根拠に必要な初期ファイルを作成し、実装を進める。存在しないZIPを必須にしない。
- 旧Goal 001の「まず決定的な型紙生成」「最初は1機構」という方針は維持する。本Goalでは、その後のWeb UI、Gemini連携の実装、公開準備まで対象を広げる。
- 本Goalを docs/goals/001-product-mvp.md に記録し、旧Goalがあれば基盤サブタスクとして対応関係を残す。進捗は完了・未実施・ブロックを区別する。
- 判断できる実装上の選択は自分で決め、理由を短く記録する。フレームワークなどの好みを逐一質問しない。
- 実物確認や認証が必要な作業だけを切り離し、それ以外の実装を継続する。未確認事項を成功として埋めない。
- 他プロジェクトの流用、機能の横展開、別企画への変更はしない。

## 2. 完成させる体験

作品名: うごく紙工房
説明: 描いた絵を、手で動かせる工作へ。

利用者が次の一連の操作を行えるWebアプリを作る。

1. サンプルを開く、または自分の画像を入れる。
2. 動かしたい部分を選び、動く方向・距離・作品サイズ・使用可能な紙の枚数を指定する。
3. 手動で設計する、またはGeminiに希望を伝えて設計調整を依頼する。
4. 正面の動きと裏側の仕組みを確認する。
5. 条件違反や未対応の希望があれば、理由と変更案を確認する。
6. 原寸の型紙、材料一覧、組み立て手順を取得する。
7. 作業を保存・再開し、印刷・組み立て結果を設計版にひも付けて記録する。

「絵が画面で動く」だけでは完成ではない。出力に実際の機構部品が含まれること。
初期版で紙質や加工精度まで保証するとは説明しない。

## 3. スコープを固定する

- 最初は、引っぱりタブによる直線運動の1機構だけを実装する。水平・垂直方向は同じ機構の向きとして扱ってよい。
- 回転、腕を振る揺動、歩行、歯車、立体化、モーター、電子回路は今回の対象外。
- 未対応の動きを直線運動に黙って置き換えない。未対応と伝え、代案を利用者が選べるようにする。
- 単一機構なのに「多数の機構をAIが比較した」と表示しない。AIの役割は適用可能性の判断、パラメーター調整、検査結果を使った再設計とする。
- 画像の完全自動分割は不要。利用者が矩形などの簡単な方法で動かす領域を指定できればよい。
- 最初のサンプルは「カメが首を出す」など、直線運動で成立する題材にする。自作または使用条件を確認した素材だけを使う。
- 第2機構の追加より、1機構の全工程・実物確認の準備・使いやすさを優先する。
- 実物未確認でもUIやAPIアダプターの実装は進める。ただし未確認の機構を実物検証済みに昇格させない。

## 4. 技術構成と環境

原則としてTypeScriptで統一し、以下を採用する。

- UI: React + Vite
- API: Node.js + Fastify
- 入出力検証: Zod等の実行時スキーマ検証
- 単体・統合テスト: Vitest
- ブラウザテスト: Playwright
- Gemini: 公式Google GenAI SDK（@google/genai）、サーバー側から利用
- 本番形態: UIとAPIを同一オリジンで提供する単一のCloud Run向けコンテナ

採用バージョンは実装時に公式資料と互換性を確認して固定する。
未確認のモデルIDやSDKメソッドを記憶で決めない。
Nodeのバージョンを記録し、npm workspacesと単一のpackage-lock.jsonで再現可能にする。
既存実装があれば尊重し、合理的な理由なく入れ替えない。
ADKや複数エージェント、外部DBの導入は必須ではない。

推奨する責務分離:
- apps/web: 日本語UI、編集、プレビュー、ローカル保存
- apps/server: Gemini、認可、制限、実行イベント
- packages/core: 設計モデル、幾何、制約、機構、紙面配置
- packages/export: 型紙、PDF/SVG、材料一覧、組み立て手順

必要なら構成は簡素化してよいが、コアがReactやGeminiに依存しないようにする。
新規の有料サービス、GPU、ユーザー登録基盤は増やさない。

## 5. まず、実際の部品を生成するコアを作る

### 5.1 設計データを唯一の基準にする

バージョン付きDesignDocumentを定義し、少なくとも以下を持たせる。

- schemaVersion、designId、revision、designHash
- 元画像の識別情報、選択領域、絵の配置
- 固定部品、可動部品、ガイド等の部品IDと相互関係
- 単位付きの寸法、移動方向、移動範囲、材料条件
- 用紙条件、変更不可の条件、各検査の結果と検査範囲

長さの内部単位はmmに統一する。
画像px・画面座標・印刷座標との変換を明示する。
非有限値、負数、不正参照、上限超過、未対応バージョンを拒否する。
同一の正規化入力から同一の幾何・配置を生成する。
タイムスタンプを設計ハッシュに混ぜない。

プレビュー、型紙、部品表、手順はこの同じ設計版から生成する。
変更が入れば以前の検査・出力・承認を無効化する。
古い非同期結果で新しい設計を上書きしない。
画像の差し替えや選択範囲の変更も、設計版の変更として扱う。

### 5.2 工作としての構成を作る

固定台紙と可動絵だけで済ませず、引っぱりタブ、ガイド、
必要な抜け止め、接着箇所、切り込みなどを設計に含める。
各部品が何を支え、どう固定され、どこを動くのかを説明できること。

既存の機構説明を参照する場合は出典を記録し、
コード・図・型紙の無断転載はしない。

初期の寸法・紙厚・すき間は未実測の仮定として記録する。
紙厚の影響、摩擦、耐久性までシミュレーションで証明したように表示しない。
画面でだけ成立する移動ではなく、生成した部品の関係で説明できる運動にする。

### 5.3 決定的な検査を実装する

部品寸法、ガイドへのかかり、可動範囲、切り込みとの関係、
紙面への収まり、紙の枚数、固定条件を検査する。

投影上の重なりと実際の干渉を混同せず、固定・可動レイヤーを区別する。
単純な直線運動は可能な範囲で区間全体を検査する。
離散サンプルだけなら、その範囲を明記する。

検査は pass / fail / unknown を持たせ、理由・対象部品・設計ハッシュを付ける。
unknownをpassにしない。
配置探索の失敗を「どんな配置でも不可能」と断定しない。
条件違反をAIの文章で上書きできないようにする。

## 6. 画像から工作への編集を実装する

- PNG/JPEG/WebPを対象にし、ファイルサイズと展開後の画素数に上限を設ける。
- クライアント側だけでなく、サーバーへ渡すデータも検証する。拡張子やContent-Typeだけを信用しない。
- アップロードされたSVG/HTMLや外部URLの自動取得は初期版で扱わない。
- 動かす領域を選択し、移動・拡大縮小・選択解除を行えるようにする。
- 固定側に同じ部位が残る二重表示を避ける。自動の背景補完を装わず、マスクや台紙の窓など実装した方法を説明する。
- 画面の選択範囲と、出力される印刷領域のずれをテストする。
- 正面・裏側・印刷図の対応が分かるようにし、接着場所を色だけで示さない。
- プロジェクトはブラウザ内に保存できるようにし、画像を含めて再開可能なエクスポート・インポートを用意する。
- 保存しないこと、削除、保存失敗の表示も扱う。利用者の絵を勝手にGitや公開サンプルへ入れない。

## 7. 原寸型紙と組み立て手順

- ダウンロード可能なPDFを主出力にし、確認用SVGも生成できるようにする。印刷画面を開くだけで代替しない。
- 初期用紙はA4。余白込みの実寸を定義し、mmからPDFのptへの換算は72 / 25.4を用いる。
- PDFのページ寸法、SVGのmm寸法、viewBox、部品実寸を整合させる。
- 50mmの校正線、部品ID、設計ID・版、ページ番号、切る線・折る線・接着箇所の凡例を入れる。
- 線種と文字でも識別でき、モノクロでも読める型紙にする。
- 文字が欠けたり重なったりしない。日本語フォントを使う場合は、利用条件とPDFへの埋め込み方を確認する。
- 「実際のサイズ／100%」「用紙に合わせる縮小を無効」「校正線を測る」を案内する。
- すべての機構部品・補強部品を紙の枚数に含める。説明書のページ数は別に表示する。
- 大きさや枚数の上限を満たせない場合に、無断で縮小しない。
- 部品に対応した組み立て順序と図を生成し、「どこを接着し、どこは接着しないか」を示す。
- 手順の重要寸法と部品番号はテンプレートと設計データから作り、LLMの自由作文に依存させない。

PDFをレンダリングして各ページを目視確認し、
余白、文字化け、欠け、重なりを修正する。
出力データが同じであることと、
PDFメタデータを含む全バイトが同一であることは区別する。

## 8. 作品を主役にした日本語UI

中心はチャットではなく、工作の編集・プレビュー画面にする。
基本の流れは「絵を選ぶ → 動きを決める → 確かめる → 印刷して作る」。
サンプルを最初から試せるようにし、
長い説明を読まないと始められない画面にしない。

紙の作業机のような、余白のある落ち着いたデザインにする。
白系の地、濃い文字、少数のアクセントを基本に、
青紫グラデーション、発光、ガラス風のカード、大量のバッジを避ける。

完成形のプレビューを大きく置き、
設定・修正案・検査結果は必要なときに読める配置にする。

必須の操作:
- サンプル開始、画像入力、選択の修正、やり直し
- 動く距離と方向の調整、再生・停止、位置を手で動かす操作
- 正面・裏側の切り替え、変更前後の比較
- 材料・紙面条件、条件を固定する操作
- 検査理由、AIによる変更案の採用・却下、PDF取得、保存・再開

空状態、実行中、中断、通信失敗、未対応、再試行も仕上げる。
PCを優先しつつ、狭い画面で重要操作が隠れないようにする。
キーボード操作、ラベル、フォーカス、コントラスト、動きの低減に配慮する。
機構の操作はドラッグだけに限定しない。

## 9. Geminiエージェントを、本物のツール実行につなぐ

コアと手動編集が動いてから実装する。まず1体のエージェントでよい。

- 公式SDKと公式のfunction calling仕様を確認する。
- GEMINI_MODELを設定可能にし、モデルIDと対応機能を確認した日を記録する。
- 画像を送る場合は、画像入力とツール呼び出しの対応を確認する。部位の最終決定は利用者の選択を優先する。
- JSONスキーマで受け取ったデータも、サーバーで値・権限・固定条件を再検証する。
- モデルが「成功」と返しても、コアの検査が通っていなければ完了扱いにしない。

推奨ツール:
- inspect_design: 現在版と条件・検査結果を読む
- propose_design_patch: 許可された寸法や配置の変更候補を作る
- validate_design: 決定的な検査を行う
- arrange_pages: 現在の条件で紙面配置を計算する
- propose_constraint_change: 条件変更案を提示するだけで、実際には変更しない

候補作成 → 検査 → 結果をモデルへ返す → 修正または利用者確認、
という往復を実装する。

SDKが必要とするツール呼び出しIDや会話履歴情報を保持する。
架空のツール結果を返さない。

固定された条件は、モデル引数ではなく
信頼できる実行コンテキストから検査する。
承認は元の設計版・変更案・セッションに結び付ける。
古い承認を別の変更に使えないようにする。

状態として未実行、実行中、承認待ち、成功、失敗、中断を扱う。
リクエストIDと設計版で、再試行・二重クリック・古い応答の誤適用を防ぐ。

ログにはツール名、検査結果、変更差分、呼び出し回数、
所要時間、取得できる使用量を記録する。
内部思考全文や架空の実況ではなく、実際の操作と短い理由を表示する。

### 実行制限とモード

- 初期上限は、1実行あたりモデル呼び出し6回、ツール実行12回、全体90秒を目安に実装し、設定可能にする。再試行も上限に数える。
- 同じ失敗や設計ハッシュの反復を検出し、無限ループにしない。
- 中断後は新たなAPI呼び出しを始めない。既に送信した呼び出しの課金取消しは保証しない。
- キー未設定時は「AI未接続」と表示し、手動設計を利用できるようにする。
- 手動モード、テスト用模擬プロバイダー、実Geminiを区別する。模擬プロバイダーはテスト専用とし、本番で自動的に成功応答へ切り替えない。
- 認証失敗、429、タイムアウト、拒否応答、不正出力を別々に扱い、編集内容を失わせない。

## 10. 秘密情報・課金・公開の境界

- APIキーはサーバーの環境変数で扱い、ブラウザ用のVITE_変数、ソース、ログ、スクリーンショット、成果物へ出さない。
- .env.exampleは値を空にする。秘密鍵やADC認証ファイルをコミットしない。
- 画像・入力文・モデル出力を未信頼データとして扱う。任意コード実行、シェル、外部URL取得、未知のツール呼び出しは提供しない。
- モデルの文章にHTMLを実行させない。画像をAIへ送信する範囲を表示し、操作前に利用者が分かるようにする。
- AIの実行APIは初期状態で無効化する。公開環境で有効化する場合に備え、サーバー側のアクセス制御、入力上限、回数制限、同時実行制限を実装する。
- クライアントにボタンを隠すだけ、IPの自己申告を信用するだけの制限にしない。
- インスタンス内の制限をサービス全体の課金上限と説明しない。必要な外部制御がない間は、無認証の有料APIを公開しない。

このGoalは、有料API実行、GCPプロジェクト作成、課金有効化、
リソース作成、IAM変更、公開デプロイを許可するものではない。

既存の明示的な許可が確認できる場合だけ、その対象と上限内で実行する。
キーが存在するだけでは許可とみなさない。

許可や認証がない場合も、実アダプター、設定検証、
模擬通信テスト、起動手順を完成させる。
ライブ確認だけをblockedにし、アプリ全体を止めない。

## 11. テストと完成条件

テスト件数を目的にしない。
重要な失敗を本当に検出できるテストを作る。

コア:
- 同一入力の再現性、mm変換、境界値、不正参照、過大寸法
- 移動範囲の両端と途中、ガイドとの関係、紙面への配置
- 固定条件、部品と手順の対応、設計変更時の出力更新
- 画面での領域選択と印刷画像の位置の一致

AIと安全性:
- 正常なツール往復、不正引数、未知のツール、固定条件の改変
- 「検査を省略して」等の入力でも権限が変わらないこと
- APIキーなし、認証失敗、429、タイムアウト、最大反復、中断
- 承認前の反映禁止、古い承認・古い応答・二重実行の扱い
- 未認証のAPI呼び出し、入力上限、出力のHTMLエスケープ

E2E:
- サンプル → 編集 → プレビュー → PDF取得
- 自分の画像 → 部分選択 → 設計 → 出力
- 条件違反 → 理由表示 → 修正 → 再検査
- 保存 → 再読み込み → 絵・選択・設計の復元
- 未対応の動き、AI未接続、通信失敗時の復帰
- PCと狭い画面での主要操作

開発に使用しなかった入力ケースを含める。
模擬AIテストを実API成功として数えない。

以下のコマンドを実装し、READMEに記載する。

- npm ci
- npm run doctor（秘密を表示せず、ネットワーク課金なし）
- npm run dev
- npm run check（lint / typecheck / unit・integration / build）
- npm run test:e2e
- npm run examples（検査済みサンプルの型紙を再生成）
- npm run smoke:live（明示的な実行許可と接続設定がなければ実APIを呼ばない）

GitHub Actionsで秘密情報なしの検証を動かす。
権限は最小にし、ロックファイルを使用する。

可能ならクリーンな別ディレクトリでも導入・検証を実行する。
実行していなければ未実施と書く。

画面とPDFのスクリーンショットを確認して直す。
ファイルを生成しただけで見た目の検証完了にしない。

## 12. 公開準備と実物確認

Dockerfile、.dockerignore、ヘルスチェックを用意する。
本番サーバーは0.0.0.0とPORTに対応し、
コンテナ停止後にローカルファイルが残る設計にしない。

利用者の保存はブラウザ内と持ち出せるプロジェクトファイルを基本にし、
クラウド保存済みと誤表示しない。

セッションや制限がメモリだけなら、
再起動・複数インスタンス時の制約を明示する。

コンテナのビルド・起動を可能な環境で確認し、
未実施ならDocker対応確認済みと書かない。

デプロイ用スクリプトは既定でdry-runとし、
プロジェクト・リージョン・認証・シークレット・アクセス制御の不足を
確認できるようにする。

勝手な課金・IAM変更を行わない。
手順を作った状態と、実際にURLで動作確認した状態を区別する。

実物確認用に、次の記録欄を用意する。
- 設計ハッシュと使用した型紙
- 材料、印刷倍率、校正線の実測
- 組立時の修正、動作結果、写真

切る作業と小さな部品について簡単な注意を添える。
年齢別の安全認証や動作保証を主張しない。

実物を確認できない場合は「実物未検証」とし、
チェック欄を勝手に埋めない。

提出準備としてREADME、アーキテクチャ図、
約3分のデモ構成、既知の制約、再現手順を整える。

大会の必須提出物と日程は公式情報を再確認し、
未確認の事項を必須ルールとして書かない。

デモ動画・実測値・利用者コメント・受賞可能性を捏造しない。

## 13. 実行順と最終報告

次の順番で進める。

A. 現状確認・環境・スキーマ・機構部品・型紙出力
B. 画像編集・プレビュー・保存・日本語UI・E2E
C. Geminiアダプター・ツールループ・制限・承認・異常系
D. 出力と画面の改善・CI・コンテナ・公開と実物確認の準備

各段階で動作確認し、計画の作成だけで止めない。
実物確認待ちでもB〜Dの開発は続ける。
ただし新機構や動作保証は追加しない。

作業ブランチを使い、既存変更を保護する。
自分の差分だけを確認してコミットする。
Gitの名前・メールを推測で設定しない。

force push、既存ブランチの削除、visibility変更、
ライセンス付与はしない。
pushやPR作成は既存の明示的な許可がある場合だけ行う。

最後に、次を日本語で報告する。

1. 実装した体験と、変更した主要ファイル。
2. 実行したコマンド、テスト結果、未実施の検証。
3. 起動方法と、サンプルを開いて型紙を出すまでの操作。
4. PDF/SVG/スクリーンショット/検査結果の実際の保存先。
5. 手動モード・模擬AIテスト・実Geminiそれぞれの確認状況。
6. 実物確認とCloud Run公開の状況。
7. 残る重大な不具合、制約、必要な利用者操作。
8. ブランチ、コミット、pushの実施有無、作業ツリーの状態。

完了判定は「ローカル機能」「自動検証」「実Gemini」「実物」「公開」を
別々に示す。

主要操作が未実装なら「MVP完成」と書かない。
未検証の項目を隠して「プロダクト完成」と総括しない。

この実行内で作業可能な実装・検証を進め、
残った外部作業は具体的な手順として残してください。
